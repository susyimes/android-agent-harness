# v0.5.2 — Phone/Web Stop quiescence and exact dispatch fencing

v0.5.2 is a backward-compatible safety patch for Android Phone Use and
Web4Agent. It gives strict hosts an awaitable Accessibility effect barrier and
closes the races around Web page-effect dispatch and visible BrowserActivity
presentation.

## What changed

- The platform-neutral `device-loop` artifact adds the optional
  `CancellableDeviceSurface`, `DeviceSurfaceEffectScope`,
  `DeviceSurfaceStopController`, `DeviceSurfaceStopHandle`, and
  `DeviceSurfaceStopOutcome` contracts. The original `DeviceSurface` interface
  and existing implementations remain source and binary compatible.
- `AccessibilityDeviceSurface` now creates one effect scope per host run. Stop
  synchronously closes admission, cancels queued Android-main tasks, and
  returns without waiting on main. Its quiescence stage completes only after
  every admitted effect exits, every already-dispatched gesture reports its
  result, and clipboard fallback cleanup/restoration has finished.
- `AndroidPhoneAgent.requestWithStopQuiescence()` feature-detects that strict
  capability, fails closed for legacy surfaces, and returns the ordinary
  `AgentRunRequest` together with its scope-owned Stop controller. A terminal
  run event automatically fences the scope before it is forwarded to the host
  listener.
- Exact Web4Agent act/eval now runs a page guard and then performs a second
  atomic check of session closure, WebView identity, one-use lease ownership,
  and page epoch immediately before JavaScript or native navigation dispatch.
  If close or replacement wins, the response is `SESSION_CLOSED`,
  `occurred=false`, and the requested click/eval/navigation is never invoked.
- WebView progress reaching 100 no longer impersonates page completion;
  `onPageFinished` or an error callback owns that transition. This removes a
  replacement-session race where `open()` could return while the document was
  still `loading` with no body.
- `Web4AgentRuntime.preparePresentation()` issues a one-shot lease with a
  Harness generation and optional host generation. BrowserActivity consumes
  it under the runtime lifecycle lock before controller creation/attach.
  Pending Stop/replacement returns `CANCELLED`; late Activity admission is
  rejected with zero old controller creation. `closeAndAwaitQuiescence()` waits
  for any already-attached Activity to detach, and an old same-session lease
  cannot close a newer generation. Existing `show(sessionId)`/`close(sessionId)`
  APIs remain compatible.
- `Web4AgentToolSet` feature-detects the optional
  `Web4AgentAcknowledgedPresenter`; strict open waits off Android main for the
  exact generation to attach before session open. Legacy presenters retain
  fire-and-return behavior.
- Development publication now uses `build/sdk-candidate-repository`. A formal
  release requires a clean Git commit and a new explicit Maven directory, then
  writes commit-bound `publisher-sidecar.json`, `publisher-sidecar.sha256`, and
  `artifacts.sha256` files. The task rechecks clean status and the exact HEAD
  after publication before writing the sidecar.

## Strict Phone Stop integration

```kotlin
val binding = phoneAgent.requestWithStopQuiescence(
    sessionId = sessionId,
    userInput = userInput,
    providerFactory = providerFactory
)
val run = agentSdk.run(binding.request)

fun stop() {
    val stop = binding.requestStop("user.stop")
    run.cancel("Stopped by user.")
    stop.quiescence.thenAccept {
        publishStopped()
    }
}
```

`requestStop` may be called on Android main. Do not block main by awaiting the
stage there, and do not publish `STOPPED` before it completes. Hosts that only
use `AndroidPhoneAgent.request()` retain the old behavior and must not claim
the stronger quiescence guarantee.

## Web Stop integration

`Web4AgentRuntime.closeAndAwaitQuiescence(presentationLease, reason)` first
fences pending/attached visible presentation and the captured strict session.
If it wins before exact dispatch, the entered tool call completes with
`SESSION_CLOSED` and zero effect. If dispatch already won, it is an admitted
operation; the host must keep that tool invocation inside its run-level
in-flight-effect barrier and publish `STOPPED` only after the invocation has
completed and presentation quiescence has completed. A new session with the
same id never grants the old one a presentation or effect lease.

## Verification

- JVM race tests cover Stop before admission, between admission and device
  dispatch, queued-main cancellation, a running main callback, clipboard
  cleanup, terminal-listener ordering, and legacy-surface fail-closed behavior.
- Deterministic Web connected tests latch after the page guard and before
  dispatch, then close the session from another thread. Back, forward, reload,
  click, and eval all return `occurred=false` with no old marker.
- A second deterministic Web connected test latches Activity admission before
  controller creation. Pending-launch timeout/cancel, late Activity, same-
  session ABA, predecessor restoration, and distinct-session replacement
  preserve exact presentation identity and quiescence. Harness launch Intents
  no longer use API-dependent `REORDER_TO_FRONT` reuse; exact leases use an
  isolated non-recents task so API 29 cannot coalesce a replacement into a
  finishing root Activity.
- `checkConnectedSample` passes on API 29 and API 34 with sample 9/9 plus the
  Web guard/presentation race suite 2/2. The Phone test uses a real
  Accessibility gesture and forced clipboard fallback on each API level.
- `checkSdk` and `checkM0` cover committed JVM ABI, unit tests, Android lint,
  independent local-Maven consumers, publication, provenance, and Android-test
  assembly.
