# 0.6.0 - Composable capabilities and current-turn history

Hosts can package tools, legacy context providers, named context sources and
optional tool-loop activation into `AgentCapability`, then compose them with
`AgentRunRequest.withCapabilities`. All admitted tools are visible from the
first provider step; the model chooses them. Composition starts no provider,
creates no runtime, preserves host budgets and approval policy, and rejects
duplicate tools, source ids and capability ids. Restricted host profiles must
explicitly admit new activation tools.

`AndroidPhoneAgent` now uses that same composition path for host extensions.
Its existing API, scoped Stop surface and Phone/Web protocols remain compatible.
The independent Maven consumer exercises the new capability API.

Both provider adapters now share one history window. A bounded multi-turn
conversation keeps the latest user request and the newest tool result in that
turn. Older tool results retain protocol-compatible placeholders. History is
trimmed only on the wire; committed transcripts stay intact. The character
budget remains soft for pinned content and required tool-result placeholders.

Stable run telemetry is emitted before legacy UI listeners, so a listener that
stops a run cannot put its start event after its terminal event. Stable event
mapping is separated from runtime lifecycle code. A provider connection completed
after SDK closure is rejected and cancelled before admission.

Validation uses `checkM0 checkSdk`: JVM and Android unit tests, API snapshots,
independent published consumers, provenance, Android lint, and debug APK/test
APK assembly. These gates do not constitute device or live-provider acceptance.

Verified on 2026-10-18: 393 unit tests passed. The API 36 emulator passed
all 13 connected tests (sample 9, published Android consumer 2, Web4Agent 2).
The combined checkM0, checkSdk and checkConnectedSample invocation succeeded.
